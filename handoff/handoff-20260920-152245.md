### Findings already supported

- `ctx.ui.addAutocompleteProvider` 可叠加 provider，其 `triggerCharacters: ["$"]` 被 Pi 收集并用于默认和自定义编辑器。无需再替换 CodexEditor。
- `pi.getCommands()` 可以筛选 `source === "skill"` 取得已发现的 skill 信息。它与 TUI slash 菜单对 `enableSkillCommands` 的过滤不同，后续应明确设置语义。
- `input` transform 在原生 skill 展开前执行。单 skill 可先转换成开头的 `/skill:name ...`，由原生链路读取正文，而不只是插入名称。
- `_expandSkillCommand()` 只展开消息开头的一次 `/skill:`。`parseSkillBlock()` 只返回一个 skill 结构。两个 XML block 以双换行连接时，第二块进入 `userMessage`；单换行时会回溯合并入首块 content。不能据此得到两个原生折叠块。
- 原生 skill 展开保存在 `role: "user"` 文本中；TUI 在 skill 分支直接构造 `SkillInvocationMessageComponent`。当前未发现公开替换 factory/registry。Markdown transformer 不处理其正文，自定义 message renderer 按 `customType` 处理 custom role，并不接管此分支。
- `SkillInvocationMessageComponent` 顶层导出，`updateDisplay` 在当前 JS 中是普通方法。因此内部补丁是可进一步验证的候选，不是已证明可发布的方案。

## Current Assumptions

前一代理提出但未确认的路线是：

1. 推荐新增上游正式 skill renderer 接口，由 codex-ui 使用。尚未设计完整 API，也未评估用户能否接受维护 Pi 定制版本。
